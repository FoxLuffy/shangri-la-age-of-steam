# C8.2 — Mod Validation & Sandboxing Design

Roadmap item: **C8.2** (Expanded Modding Ecosystem). Depends on C8.1 (guide/schema).

## Goal
Validate uploaded mods before applying them, returning all problems at once so uploaders
get actionable feedback and malformed mods never touch the database.

## Decisions (confirmed)
- **Collect all errors, atomic reject**: validate the whole file; on any error, return a
  list of messages and commit nothing.
- Checks in scope: **schema** (required fields, types, unknown fields, enum), **in-file ID
  uniqueness**, **referential existence**. Content-safety (length limits / prohibited
  terms) is out of scope for this item.
- Failures return **HTTP 400** with `detail` = list of human-readable strings (matches the
  guide and the Settings UI which displays `detail`).

## Module: `backend/mod_validation.py`
Pydantic models with `extra="forbid"` mirroring the supported entities:
- `FactionMod(id, name, description)`
- `LocationMod(id, name, description, faction_id?)`
- `NpcMod(id, name, traits?, current_dialogue?, disposition?, memories?, location_id?,`
  `faction_id?, custom_system_prompt?, speed?, hp?, max_hp?, armor?, status_effects?, is_hostile?)`
- `ItemMod(id?, name, description?, category: ItemCategory)`

`validate_mod(data, session) -> list[str]`:
1. `data` must be a JSON object; each present known section must be a list.
   Unknown top-level sections are ignored (recipes/bounties are Planned).
2. Schema-validate each entity via its model; format pydantic errors as
   `"{section}[{i}]{ (id)}: {field} {message}"`.
3. **ID uniqueness** within the file: duplicate `id` across factions/locations/npcs, or
   duplicate `name` across items → error.
4. **Referential**: build id sets from the DB + this file, then require (when the field is
   present and non-null): `location.faction_id` ∈ factions, `npc.location_id` ∈ locations,
   `npc.faction_id` ∈ factions. Otherwise → error naming the dangling reference.

Returns `[]` when the mod is valid.

## Endpoint change: `backend/main.py` `/modding/upload`
- Parse JSON; invalid JSON → `HTTPException(400, "Invalid JSON: ...")`.
- `errors = validate_mod(data, session)`; if `errors` → `HTTPException(400, detail=errors)`.
- Otherwise apply exactly as today (upsert factions → locations → npcs → items).

## Tests: `backend/tests/test_mod_validation.py`
- `validate_mod` on `docs/mods/example_mod.json` returns `[]`; endpoint upload → 200.
- Missing required field (faction without `name`) → 400, message mentions `name`.
- Wrong type (`disposition: "high"`) → 400.
- Unknown field (`faction.colour`) → 400.
- Invalid `item.category` → 400.
- Duplicate id within the file → 400 mentions "duplicate".
- `npc.location_id` referencing a nonexistent location → 400; referencing a location
  defined earlier in the same file → valid.
- A file with two distinct problems returns ≥2 messages (collect-all).

## Out of scope
- Content-safety (lengths, prohibited terms), dependency chains (C8.4), ratings (C8.3),
  making recipes/bounties moddable.

## Acceptance
- Malformed mods are rejected atomically with a list of clear messages; valid mods still
  apply. Full suite green; `ruff` clean.
